# Проверки и обновления

- Для любых изменений интерфейса обязательно читать и соблюдать [DESIGN.md](DESIGN.md). Применять общие компоненты и правила на всех страницах проекта, а не исправлять оформление только в одном месте.

- Перед завершением изменений запускать `./scripts/validate.sh --tests`.
- При изменениях интерфейса запускать скриншотные тесты Playwright из `tests/ui` на всех разрешениях, просматривать снимки и повторять тесты без обновления эталонов. Активная вкладка выделяется красным и имеет `aria-current="page"`.
- SonarQube Cloud обязателен: проверять весь проект и всю ветку `main`, включая старый код, а не только New Code. Исправлять все открытые замечания и проверять Security Hotspots. Не скрывать проблемы исключениями, отключением правил или массовым изменением статусов.
- При добавлении новых каталогов исходников включать их в `.sonarcloud.properties`; тесты анализируются отдельно через `sonar.tests`.
- После изменений получать свежий анализ соответствующего коммита. Quality Gate должен пройти; открытых неисправленных замечаний быть не должно. Если анализ недоступен, явно сообщать об этом и не объявлять проверку пройденной.
- Релиз разрешён только после успешных локальных проверок и SonarQube. Создание релиза требует явного указания пользователя; текущая задача релиз запрещает.
- Обновление сервера: сначала согласованная резервная копия данных, конфигураций и используемых образов. Сохранять настройки сервера, ключи, устройства и сторонние сервисы. После обновления проверять доступность, авторизацию, DNS и маршрутизацию; при сбое восстанавливать согласованную пару образов и данных.
- Не помещать приватные конфиги, ключи, cookie и токены в Git, ответы, логи или заметки. Документация должна быть краткой, понятной и описывать назначение сервиса нейтрально.
