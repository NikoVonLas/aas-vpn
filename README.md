# AAS VPN

Сервис защищённых подключений на AmneziaWG с управлением аккаунтами, устройствами и маршрутами. Доступ задаётся ролями; способы входа настраиваются отдельно от VPN-конфигураций. AdGuard Home обслуживает DNS.

## Установка

Нужны Linux с установленным модулем AmneziaWG, root и DNS-записи доменов на сервер. Caddy использует TCP 80/443, VPN — UDP 443; дополнительный UDP-порт задаётся в `.env`.

```bash
git clone https://github.com/NikoVonLas/aas-vpn.git
cd aas-vpn
cp .env.example .env
# Заполните .env и проверьте внешний интерфейс в config/sing-box.json.
sudo ./scripts/deploy.sh
cd /opt/aas-vpn
docker compose exec portal python auth.py create admin
```

В `.env` задайте `VPN_DOMAIN` (адрес VPN), `PORTAL_DOMAIN` (портал), соответствующие `*_SITE_ADDRESS` для Caddy и параметры кампании Zvonok. `COOKIE_DOMAIN` нужен только для удаления старых административных cookie. Другой каталог установки: `AAS_INSTALL_DIR`.

За существующим Caddy используйте `COMPOSE_FILE=compose.yml:compose.edge.yml`, локальные адреса публикации портов и существующий `VPN_NETWORK_NAME`. Серверные настройки overlay хранятся в `data/adguard/` и `data/sing-box/config.json`; имена прежних volumes задаются согласно `.env.example`.

AdGuard настраивается через SSH-туннель `ssh -L 3000:127.0.0.1:3000 root@SERVER`: откройте `http://localhost:3000`, задайте DNS `0.0.0.0:53`, upstream `10.42.42.1:5353`–`:5356`, режим `parallel` и timeout `5s`.

Для подключения используется [AmneziaVPN](https://amnezia.org/ru/downloads). Кнопка «В AmneziaVPN» в карточке устройства открывает приложение через `vpn://`; если браузер не передаёт ссылку приложению, диалог позволяет скопировать ключ. QR содержит тот же ключ. Подробные шаги доступны в кабинете. Выданные ранее конфиги продолжают работать.

## Управление

Общий вход: `https://PORTAL_DOMAIN/`. Одна форма принимает логин с паролем либо телефон/почту без пароля для подтверждения; ключ/passkey доступен кнопкой в этой же форме. Поля, подписи и кнопки автоматически учитывают основные способы, разрешённые назначенными ролями активных аккаунтов, и включённые модули. Стандартные роли — администратор и пользователь. По умолчанию вход по логину и паролю, у администратора обязательна 2FA. Создание аккаунта учитывает способы его роли. При миграции сохраняются прежние реквизиты и назначенные дополнительные права; роль владельца объединяется с администратором. Аккаунты получают постоянные ID без объединения записей по имени.

- **Пользователи:** поиск по имени и реквизитам, фильтры состояния и роли, по 25 записей на страницу. Создание и редактирование раскрываются в списке тем же компонентом, что роли, выходы и способы входа. В карточке доступны устройства, маршрутизация и отдельное действие администратора «Восстановление»; здесь же назначаются роли. Имя устройства и альтернативный выход сохраняются вместе. Конфигурация и QR требуют отдельного права.
- **Роли и доступ:** создание, копирование и настройка ролей; несколько ролей на аккаунт, область «свой аккаунт», выбранные аккаунты или глобально. Права и разрешённые способы входа складываются; обязательная 2FA действует, если её требует любая роль. Только администраторы меняют роли, назначения и административные аккаунты. Последнего активного администратора отключить или лишить роли нельзя.
- **Способы входа:** глобальные переключатели всех пяти способов: пароль, passkey, приложение-аутентификатор, Zvonok и SMTP. Отключённый способ недоступен для входа и подтверждения, даже если разрешён ролью; сохранённые реквизиты не удаляются. Zvonok сохраняет действующие настройки; почта изначально выключена. Для SMTP обязателен проверяемый TLS. Письмо содержит код и ссылку на 10 минут; использование одного погашает оба. Ссылка подтверждается кнопкой в открывшем её браузере.
- **Безопасность профиля:** разрешённые реквизиты, приложение-аутентификатор (TOTP), несколько ключей/passkeys, резервные коды и отзыв сессий. До завершения обязательной 2FA доступны только подтверждение и необходимая настройка. WebAuthn проверяет challenge, подпись, origin, RP ID и user verification; ключ с PIN/биометрией может удовлетворять 2FA. [Спецификация WebAuthn](https://www.w3.org/TR/webauthn-3/).
- **Маршрутизация:** сначала правила устройства, затем аккаунта, затем глобальные. Внутри уровня действует специфичность доменов и IPv4/CIDR; при равенстве выбирается обычный выход. Без совпадений используется основной VPS. Правила аккаунта и устройства изначально пусты.
- **альтернативный выходы:** назначение устройства → дефолт аккаунта → глобальный дефолт. Недоступные выходы пропускаются; после восстановления возвращается более приоритетный. Если доступных альтернативный выходов нет, RU-трафик блокируется. Проверки выполняются каждые 15 секунд с порогом двух неудач/успехов.

Отзыв права сохраняет маршруты и назначения, запрещая дальнейшее изменение. Для сброса очистите соответствующую форму отдельным действием. Смена реквизитов входа и альтернативного выхода не требует переимпорта VPN-конфига. Перед отключением способа входа сначала разрешите и настройте замену. Изменения доступа и критических настроек требуют свежего подтверждения входа. После подтверждения открывается исходный редактор; сохранение нужно повторить явно.

Примеры Keenetic: [сервер](examples/wg-ru-keenetic-vps.conf.example), [роутер](examples/wg-ru-keenetic-router.conf.example). IPv6 отключён. Контроллер использует `amneziawg-tools 3.0.20260805`, маршрутизатор — `sing-box 1.13.15`; версия утилит не означает включение протокола AWG 3.x.

## Обновление и восстановление

Запускайте `sudo ./scripts/deploy.sh` **из отдельной копии репозитория**. Скрипт собирает образы, сохраняет серверные настройки и делает согласованную резервную копию образов и данных. При переходе с wg-easy переносит всех администраторов и клиентов, сверяет конфиги с прежним API. Ключи, телефонные аккаунты и назначения сохраняются; администраторы входят заново прежним паролем и TOTP.

```bash
cd /opt/aas-vpn
sudo ./scripts/backup.sh
sudo ./scripts/rollback.sh /opt/aas-vpn/backups/YYYYMMDDTHHMMSSZ
# Восстановление через SSH со сбросом вторых факторов и веб-сессий:
docker compose exec portal python auth.py recover admin
```

Откат требует бэкап с файлом `COMPLETE` и восстанавливает образы вместе с данными. Аккаунты, роли, реквизиты, подтверждения и отзываемые сессии находятся в защищённом `auth.db`; устройства, лимиты и маршруты — в `portal.db`. Миграция обеих баз повторяема и использует общую SQLite-транзакцию с журналом отката. Старые веб-сессии завершаются, VPN-ключи сохраняются. Маршрутизатор не получает доступ к `auth.db`. Авторизация и ключи находятся в отдельных защищённых volumes; портал управляет туннелем через локальный Unix-сокет. Владелец также может выдать одноразовый код восстановления на 10 минут: он открывает только настройку реквизитов. Реальные конфиги, `.env`, ключи и резервные копии в Git не добавляются.

## Проверки

Установите зависимости `portal/requirements.txt`, `tests/requirements.txt`; нужны также Node.js и Compose CLI. Запустите `./scripts/validate.sh --tests`, [скриншотные тесты Playwright](tests/ui/README.md) и [Linux-проверки](tests/LINUX.md). Правила интерфейса — [DESIGN.md](DESIGN.md). Для принятия изменений обязателен свежий успешный SonarQube всего `main` без открытых замечаний; требования — [AGENTS.md](AGENTS.md). Релиз создаётся только по отдельному указанию.

Объединение телефонного аккаунта с единственным администратором выполняет `portal/account_merge.py --auth-db PATH --portal-db PATH --phone NUMBER`: сначала проверка с откатом, затем `--apply` после согласованной резервной копии остановленного сервиса. Эта явная операция задаёт серверную политику: пользователь — телефон, администратор — телефон или пароль с обязательной 2FA; конфликты отменяют всю транзакцию. VPN-устройства и ключи сохраняются, активные сессии объединяемых аккаунтов завершаются.
