# Приёмка на отдельном Linux/Docker-стенде

Эти проверки требуют работающего Docker на Linux, двух реальных RU-туннелей и двух подключённых AWG-клиентов. Они не заменяются локальными unit-тестами и не были выполнены на macOS без Docker-движка. Не запускайте сценарии отключения нод на рабочем сервере с пользователями.

1. До обновления создайте два устройства в старом стеке, сохраните их конфиги приватно и запишите image ID wg-easy. Запустите новый deploy из отдельного checkout. Убедитесь, что бэкап содержит `COMPLETE`, оба устройства подключаются со старыми конфигами, имена и ключи сохранились.
2. Проверьте `docker compose ps`, `docker compose exec sing-box sing-box check -c /router-state/working.json`, `docker compose exec awg2 iptables -t nat -S POSTROUTING` и `docker compose exec sing-box nft list table inet aas_guard`. Исключение MARK/RETURN должно предшествовать MASQUERADE; bridge в guard должен совпасть с `ip route get 10.42.42.45`. `ip route get <VPN-IP клиента>` должен указывать через контейнер AWG. При `tcpdump -ni sbtun0` исходные адреса должны отличать клиентов.
3. Добавьте RU-выход B, оставьте исходный A дефолтом, назначьте B первому устройству и «По умолчанию» второму. Добавьте IP сервиса проверки внешнего IP в список «Через RU» и запросите этот сервис с обоих клиентов. После двух проверок через туннели внешние IP должны соответствовать B и A. Затем добавьте более точное доменное правило «Через обычный выход»: этот запрос должен показывать VPS на обоих клиентах. Проверьте DNS через `10.42.42.44` и нормальное открытие сайтов.
4. Смените дефолт на B: второе устройство переключается без переимпорта, явное назначение первого сохраняется. Верните A дефолтом. Отключите peer B на удалённой ноде; через две неудачные проверки (обычно до 40 секунд) первое устройство должно показывать A и «резервный режим». Включите B; после двух успехов возвращается B. Отключите одновременно A и B: RU-запросы должны завершаться ошибкой, обычные запросы — работать через VPS.
5. При здоровых A/B запустите повторяющиеся запросы на обоих клиентах. Выполните `docker compose stop sing-box`, затем `docker compose start sing-box`. Во время остановки интернет-запросы клиентов должны не проходить, ни один ответ сервиса RU-проверки не должен показывать VPS. Проверьте перезапуск всего Docker и перезагрузку стенда: AWG должен ждать guard с новым boot ID.
6. Замените B валидным конфигом с ListenPort, уже занятым другим сервисом стенда. `sing-box check` может принять его, но запуск должен завершиться ошибкой; портал показывает ошибку применения и прежний рабочий выход продолжает работать. Исправьте порт: применение проходит. Повторите при перезапуске самого контроллера, пока ошибочная версия остаётся сохранённой. Не выводите `working.json` или вывод проверки реальных секретных конфигов в общие логи.
7. Проверьте обычный WG с Endpoint и Keenetic с ListenPort без Endpoint. Keenetic инициирует туннель и поддерживает keepalive; UDP-порт VPS открыт. Дождитесь двух успешных HTTPS-проверок. Убедитесь, что DNS из импортированного конфига не заменил AdGuard.
8. В браузере войдите администратором с паролем/TOTP. Нажмите «Выйти» сразу после входа и повторите после сохранения пользователя через AJAX. В Network должен быть обычный `POST /admin/logout`, затем `/admin/login`. Удаляются общая и host-only cookie `wg-easy`; повторный `/admin` требует входа. Проверьте кнопку с собственным `formaction`, валидацию лимита, а также сохранение после удаления cookie в DevTools — должен произойти полноценный переход ко входу.
9. Выполните `scripts/rollback.sh` с сохранённым бэкапом. Сверьте фактический image ID с исходным, оба старых устройства и общий вход. Перезапустите systemd/watchdog и убедитесь, что сохранённая пара образов и данных остаётся активной. Не восстанавливайте одну базу или один образ отдельно.

Запишите дату, версии ядра/Docker/Compose, результаты и IP нод в закрытый журнал стенда; не добавляйте приватные конфиги и ключи в Git.

## Собственный контроллер AmneziaWG

Выполните `python3 tests/guard_linux.py` от root с образом `aas-vpn-router:native-test`. Проверка в отдельных внутренних Docker-сетях воспроизводит подключение через DNAT с внешнего UDP 443 на внутренний 1234. Ответы туннеля должны проходить после создания guard, а прямой трафик контейнера и VPN-клиента — блокироваться, в том числе с исходным портом 1234. Подключение внутри одной Docker-сети не заменяет эту проверку.

Соберите `docker build -t aas-vpn-awg:native-test -f awg/Dockerfile .` и выполните от root `python3 tests/native_linux.py`. Проверка создаёт отдельную внутреннюю Docker-сеть и два клиента с одноразовыми ключами. Она проверяет передачу через туннель, откат ошибочного конфига, удаление клиента, перезапуск и ожидание актуальной защиты ядра. После проверки тестовые контейнеры, сеть и ключи удаляются. Рабочий VPN и его ключи не используются.

Миграция выполняется при остановленных изменениях: `docker compose --profile migration run --rm migrate-native` проверяет исходные базы без записи, а `--apply` переносит данные в новые volumes. Deploy дополнительно сравнивает все конфиги с экспортом старого API. Не запускайте два рабочих сервера с одинаковыми ключами одновременно.

## Аккаунты, роли и три уровня маршрутизации

До установки новой версии выполните повторную миграцию согласованной копии `portal.db` и `auth.db`. Сравните все прежние записи устройств, ключи, лимиты, назначения и правила; пароль и TOTP прежнего администратора должны сохраниться. Телефонные аккаунты получают только телефонный основной вход. Старые веб-сессии должны завершиться.

На изолированном стенде проверьте устройство → аккаунт → глобальные правила, включая конфликт менее специфичного правила устройства с более специфичным глобальным. Сопоставьте реальные DNS-запросы и внешние IP двух временных клиентов через опубликованный UDP 443. Для RU-цепочки назначьте три разные ноды: устройство, аккаунт и глобальный дефолт. Поочерёдно отключайте и восстанавливайте их, проверяя две неудачи/успеха с интервалом 15 секунд, пропуск повторов и блокировку при отсутствии доступного выхода. Рабочие пользовательские ноды для этого не отключаются.

Сравните прежний и новый образы на одном Linux-стенде с одинаковыми клиентами, маршрутами и выходами. После прогрева чередуйте версии минимум в пяти повторных замерах: медианная пропускная способность, p95 установки соединения, CPU/RAM и время применения конфигурации. Повторите с увеличенными списками и числом устройств. Для текущего масштаба допустимы снижение медианной скорости не более 5% и увеличение p95 не более 5 мс. В отчёте укажите конфигурацию стенда, нагрузку и разброс; локальный тест компиляции маршрутов не заменяет сетевое измерение.

Перед открытием обновления проверьте вход владельца прежним паролем/TOTP, прежний телефонный вход, области ролей, отдельное право конфигурации/QR и отзыв сессий. Владелец отдельно регистрирует и проверяет реальный YubiKey. Установка требует согласованной резервной копии образов и обеих баз и свежего успешного SonarQube всего `main`; при неудаче восстанавливается согласованная пара образов и данных.

Для отдельной проверки решений работающего sing-box выполните в проверочном образе маршрутизатора `python tests/routing_runtime_linux.py`, примонтировав исходники только для чтения. Проверка использует SOCKS-вход и локальные тестовые адреса выходов: она проверяет реальные совпадения правил и действия, включая приоритет уровня над специфичностью, RU-цепочку и блокировку. Внешняя сеть и реальные ключи не нужны. Это проверка маршрутизатора; она не заменяет приёмку туннелей, интервалов контроля доступности и сквозные замеры через VPN.
